# ADR-0029: 生産性の画面に「流れ」と「メンバー」を足す

- 状態: 提案
- 日付: 2026-11-12

## 背景

生産性の画面は、トークン・金額・PR・手戻り・助けを求めた数を、日ごとと内訳で見せていた。チームが速く進んでいるか、チケットが溜まっていないか、どこで待っているか、誰が動いているかは分からなかった。とくに、確認で見つかった範囲外のことからチケットが増え続け(全体の 7 割)、待ちの列が伸びていたことに気づけなかった。

## 決定

記録(tickets・runs・events・decisions)から毎回数え、集計の表は作らない(docs/design.md 9.2)。

- 「流れ」のタブ(最初に開く)
  - 時間あたりの merge(直近 24 時間。チームが動いていた時間あたりと、24 時間ならし)
  - 入った数 / 片付いた数(24 時間)と、その差(溜まっているか)
  - リードタイム(入ってから merge)・サイクルタイム(取りかかってから merge)・merge 待ち(確認が済んでから merge)の中央値と 90 パーセンタイル
  - フロー効率・一発で通った割合(差し戻し・衝突・CI の戻りなし)・責任者を待った時間
  - 直近 48 時間の 1 時間ごと: 入った・片付いた・未完了・merge・起動・金額
  - どこから入ったか(企画・確認で見つかった範囲外のこと・切り出し・main の CI・手で足したもの)と、それぞれの未完了
  - 工程ごとの仕掛かりと、長く開いているチケット
- 「メンバー」のタブ: メンバーごとの稼働率(直近 24 時間、チームが動いていた時間に対して)・起動・動いていた時間・金額・エラー・merge まで持っていった数。役割ごとの起動の長さとエラーの割合。

「片付いた」は merge・すでに入っていた・取りやめ。時刻の記録が無い古い取りやめは、入ったときに片付いたとみなす。

## 結果

- 入る数と片付く数の差、どこから増えているかが見えるので、チケットの増えすぎに早く気づける。
- リードタイムとサイクルタイムの差で、取りかかる前の待ちが大きいことが分かる。
- 画面を開くたびに記録を数え直す。チケットと起動が数千件の規模までは問題ない見込み。

## 追記: 編成を変えた印は、日ではなく時刻の位置に置く(#46・#94)

- フロー効率の推移には、編成の版が上がった印(連絡経路 / 流れ / 島。ADR-0043・0055)を縦の点線と札で置く。
- 最初は日の並びの軸に置いたので、**同じ日に何度か変えると同じ位置の線に重なった**(#46 は札を段に積んで読めるようにした)。#94 で、**横軸を時刻の連続した軸**(`ui/src/efficiencyAxis.ts`)にし、版が上がった時刻(`formationMarks[].at`)の位置に置く。同じ日に何度変えても別の位置に出る。
- 効率の点は日ごとの集計のまま、**その日の最後の merge の時刻**(`efficiencyDaily[].at`)に置く。札の詳細に時刻(11/14 15:30)を出し、期間が短いときは軸の端も時刻まで出す。見出し・文言は「編成を変えた時」にそろえる。
- 採らなかった案: **効率の点も時刻ごとに出す**(効率は日ごとの集計で、集計の単位は変えない)。**日の軸のまま、同じ日の札を積む**(位置の前後関係が分からず、版と効率の変化の順が読めない)。
- 効率の記録も編成の版も無いときは、中身の無い枠を出さず、枠ごと出さない(#81)。
