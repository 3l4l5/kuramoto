# ADR-0030: 既存のリポジトリの続きから始められるようにする

- 状態: 提案
- 日付: 2026-11-12

## 背景

企画スタジオは「一から企画して作る」前提で、企画担当は会話から要件を起こし、リポジトリを読まなかった。要件の段階は省けないので、既にあるプロダクトに使うと、責任者が既にある機能まで一から説明し直すことになった。リポジトリの開いている PR や Issue(途中の仕事)を引き継ぐ仕組みも無く、エージェントの作業場所からは GitHub が見えないので、担当が自分で拾うこともできなかった。

## 決定

- プロジェクトを作るときに、始め方を「新しく作る」と「既存のリポジトリの続きから」から選べるようにする(設定 `origin = existing`)。
- 既存のリポジトリの続きからなら:
  - Kuramoto が GitHub から、登録したリポジトリの開いている PR と Issue を取ってきて控える。Issue は既定でラベル `kuramoto` の付いたものだけ(空にするとすべて)。古い Issue まで一気にチケットになるのを避けるため。
  - 企画の各段階の担当には、聞き取りから作るのではなく、リポジトリ(README・docs・コード・設定)を読んで今の状態を下書きに起こすよう頼む。要件は、実装済みのものに「済: 」を付けて、残っているものと分ける。コードから決めきれないことだけを未決にする。責任者は下書きを確かめ、違うところだけ直して合意する。
  - 画面の試作は、既にある画面と重なるので既定で省く(企画スタジオで戻せる)。
  - チームに渡すとき、リーダーは:
    - 開いている PR を `adopt_pr` でチケットにし、確認の最初の工程から続ける(差し戻されたら、開発の島の人が PR のブランチの続きから直す)
    - Issue を `create_ticket` の `issue` 付きでチケットにする。そのチケットの PR には `Closes #番号` を付ける
    - 「済: 」の要件はチケットにしない。残っている要件はチケットにする

## 結果

- 既存のプロダクトでも、責任者は下書きを確かめるだけで始められる。
- 途中の PR は捨てずに確認から続き、Issue は merge で閉じる。
- 取ってくるのは作ったときの 1 回だけ。後から開いた PR・Issue は拾わない(必要ならチャットでリーダーに頼む)。

## 追記: 後から開いた Issue は見回りで拾う(#79)

「取ってくるのは作ったときの 1 回だけ。後から開いた PR・Issue は拾わない」は、**Issue については ADR-0051 で変えた**(見回りの周期で新しい Issue を拾い、リーダーが振り分ける)。PR は今も、作ったときの 1 回だけ。
