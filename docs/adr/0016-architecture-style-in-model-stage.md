# ADR-0016: アーキテクチャスタイルは「アーキテクチャとデータ」の段階の最初に決める

- 状態: 承認
- 日付: 2026-11-08

## 背景

企画スタジオでは、インフラ(どこで・どう動かすか)とドメインとデータ(何をどう持つか)は決めていたが、その間にある「どう組み立てるか」(モノリスかサービス分割か・モジュールの分け方・依存の向き・API の形・フロントの作り・使う技術)に合意する場が無かった。決めないまま実装に入ると、チケットごとに作り方がばらつき、開発・レビューのエージェントが毎回別の前提で判断する。

## 決定

- 「ドメインとデータ」の段階を「アーキテクチャとデータ」に改め、その最初にアーキテクチャスタイルを書く。段階の中の順番は アーキテクチャスタイル → ドメインモデル → 作る / 既存を使う / 作らない → データ設計。
  - 段階を新しく増やさないのは、アーキテクチャスタイルとドメインの境界・データ設計は互いに強く関わり、まとめて 1 回合意するほうが食い違いにくいため。
- アーキテクチャスタイルで書くこと: スタイルと選んだ理由・選ばなかった案、モジュールと責務(どのリポジトリに置くか)、守る原則(依存の向きなど)、API の形、フロントの描画方法と状態の持ち方、使う技術と理由。
- インフラで決めたことを前提にし、既にあるコードがあればその作り方に合わせる。
- 新しく技術を選ぶ必要がある領域(言語・フレームワーク・DB・主要なライブラリなど)だけ、技術選定をする。候補を 2〜3 個、その領域で効く評価軸(既存との相性・慣れ・運用・費用・成熟度とライセンス・性能など)で比べ、選んだものと理由を残す。既存やインフラで決まっている領域は選定しない(2026-11-08 追記)。
- サービスを分ける・新しい言語やフレームワークを入れるなど、後から戻しにくい選択は責任者の未決に入れる。
- 担当はアーキテクトの広([ADR-0009](0009-architect-and-domain-first.md))。

## 結果

- チームに渡すチケットが、同じアーキテクチャの前提を持てる。
- 設計書のエクスポートにアーキテクチャスタイルの節が入る。
- 段階の中身が増えるので、合意までが長くなる。お任せにすれば軽くできる。

## 検討した別案

- **インフラとドメインとデータの間に独立した段階を置く**: アーキテクチャだけを省く・お任せにできるが、ドメインの境界やデータ設計と別々に合意することになり、食い違いやすい。
- **インフラの段階に含める**: 動かし方と組み立て方が混ざり、インフラを省いたときにアーキテクチャも決まらなくなる。
