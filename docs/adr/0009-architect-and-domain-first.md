# ADR-0009: アーキテクトを置き、ドメインモデルから設計する

- 状態: 承認
- 日付: 2026-11-07

## 背景

DB 設計や「作るべきか作らないべきか」の判断を慎重にしたい。AI のチームは放っておくと新しいサービスや表を安易に作る。

## 決定

- アーキテクトを置き、要件定義から加わる。
- 順番は(アーキテクチャスタイル → [ADR-0016](0016-architecture-style-in-model-stage.md))ドメインモデル(用語・集約・守るルール・状態の移り変わり・境界)→ 機能ごとの「作る / 既存を使う / 作らない」→ データ設計(表・列・マイグレーションが戻せるか)。
- 新しいサービスや表は安易に作らない。作らない選択肢を代わりの手段と一緒に示す。
- 戻せない変更と「作らない」提案は、責任者の未決に入れる。未決が残る間は確定できない。判断の結果、聞く意味がなくなった未決は理由を添えて取り下げる。
- オフィスではデータや約束に触れるチケットを着手前に確認する(範囲はつまみ)。
- 既定のモデルは Opus 5.5、考える深さは xhigh(慎重さ優先)。

## 結果

- 新しいサービスや表の乱立を防ぐ。
- 企画の段階が長くなる。省く・お任せにする選択肢で軽くできる([ADR-0008](0008-planning-studio-gates.md))。

## 検討した別案

- **リーダーや企画担当が兼ねる**: 要件を詰める対話・チケットを回す仕事と、設計の判断は性質が違う。
