# ADR-0062: Cookie が担当の別ポートのサーバーに届くこと自体を無くす — 検討(オリジンごとの資格情報か、鍵の署名か)

- 状態: 採用(「決めてもらいたいこと」1〜3 はリーダーの仮決定。責任者の確認待ち。責任者の回答で変わったら作り直す)
- 日付: 2026-11-14
- チケット: #106(#104 のレビュー・QA で見つかった。#108 を統合。ADR-0061 の「選ばなかったこと」「残ること」の続き)

## 背景

ADR-0061 で、Cookie には合言葉ではなくセッション ID(8 時間・失効できる)を入れ、成果物は `127.0.0.1` と別のホスト名(`localhost`)で開くようにした。
しかし Cookie は**ホスト名だけで決まり、ポートで分けられない**。次のどれかがあると、`127.0.0.1:4300`(本体)の Cookie が、担当が立てた `127.0.0.1:<任意のポート>` のサーバー(=担当のコード)に送られ、担当が ID を取れる。

- 担当が成果物を `127.0.0.1:…` で案内する。
- 責任者が成果物を `127.0.0.1` で開く(QA で見つかった #108)。
- 担当が `localhost` のページから `127.0.0.1` へ飛ばす(SameSite=Strict でも、同じサイト内の取得には付く)。

ID が漏れると、8 時間か失効(`revoke-all`・再起動)まで、担当が本体の API(チケットの操作・merge)を使える。ADR-0061 は被害を小さく・止められるようにしたが、**届くこと自体は防げていない**。守りが責任者の URL の開き方に掛かるのも変わらない。

原因は Cookie の性質にある。ブラウザが送り先を決め、サーバー側では「ブラウザから来た」と「担当が貼り直した」を見分けられない。直すには、次のどちらかが要る。

- (甲)資格情報を、**ポートまで含むオリジンごと**に分かれる場所に置く(担当の別ポートのサーバーには、そもそも届かない)。
- (乙)資格情報を、**取り出せない鍵**にして、リクエストごとに署名する(届いても、鍵が無いので使えない)。

## 今の作りで、変えるときに効くところ(調べたこと)

- 画面(`ui/`)の API 呼び出しは、`ui/src/api.ts` の `fetch` 1 か所に集まっている。ヘッダーを足すのは容易。
- ヘッダーを付けられない読み込みは、次だけ(`EventSource`・`WebSocket` は使っていない)。
  - 画面のファイル: `index.html`・JS・CSS・フォント(`serveStatic`。今は合言葉の対象)。
  - `<img src="/api/projects/:id/design-images/:id">`(`ui/src/Ticket.tsx` の 2 か所)。
  - `<a href="/api/projects/:id/studio/export(.zip)" download>`(`ui/src/studio/Studio.tsx` の 2 か所)。
- 画面は React で、`dangerouslySetInnerHTML`・`innerHTML` を使っていない(XSS で JS を実行される入り口が今は無い)。Content-Security-Policy も出していない。
- 画面の URL の `#` 以降は、画面のルーティング(`#/p/:id` など)が使っている。
- 本体には、セッションの発行・失効の土台(`src/sessions.ts`、`DELETE /api/session`、`POST /api/session/revoke-all`)が既にある。

## 案

### 案 A: `localStorage` にセッション ID を持ち、`Authorization: Bearer` で送る(甲)

- 端末に出す URL は `http://127.0.0.1:4300/#k=<合言葉>` とする。`#` 以降は**サーバーにも、Referer にも、ほかのオリジンにも送られない**。画面の最初の JS が、`#k=` を読んで `history.replaceState` で消す(ルーターが動く前に)。
- 画面が `POST /api/session`(合言葉を `Authorization: Bearer` で)を呼び、本体が新しいセッション ID を返す。画面は `localStorage`(オリジンごと)に入れ、以後の `api()` が `Authorization: Bearer <ID>` を付ける。Cookie は使わない。
- 担当の別ポートのサーバーは、オリジンが違うので、この `localStorage` を読めない。`Cookie` ヘッダーも無い。担当のページが本体へ cross-origin で取りに来ても、本体は CORS ヘッダーを出さないので読めず、ID も付かない。
- ついでに、CSRF(他のサイトからの書き込み)の経路が無くなる(資格情報が自動で付かないので)。`x-kuramoto` ヘッダーは、そのまま残してよい。
- 変えるところ:
  1. 本体: `allowed()` が、ID を `Authorization: Bearer`(合言葉・セッション ID のどちらか)で受ける。`POST /api/session` を足す。`Set-Cookie` と `?token=` の 303 を無くす。前の版の `kuramoto_session` / `kuramoto_token` の Cookie は、消す応答だけ残す(一度)。
  2. **画面のファイルは、合言葉なしで配る**(`<script type="module" src>` は Authorization を付けられない)。配るのは `index.html`・JS・CSS・フォントだけで、データは含まない(`/api/` は今までどおり認証)。「画面のすべてに合言葉」(ADR-0059)から、「API のすべてに合言葉」に変わる。担当のシェルから `curl localhost:4300/` で画面のコードが読めるが、画面のコードは Kuramoto のリポジトリと同じで、秘密ではない。
  3. 画像は `fetch`(Authorization つき)→ `blob:` URL にする小さな部品(`AuthImage`)に替える。ダウンロードは `fetch` → blob → 一時の `<a download>` にする。
  4. 画面が 401 を受けたら、`localStorage` の ID を捨てて、今の「合言葉つきの URL を開いてください」の案内を出す(今の `isUnauthorized` の仕組みをそのまま使える)。
- 弱いところ: `localStorage` は JS から読める(HttpOnly を失う)。画面に XSS があると、ID を盗まれる。今の画面は React で、XSS の入り口が無いが、担当が書く文(チケットやチャット)を多く描く画面なので、保険に **CSP**(`script-src 'self'`、`object-src 'none'`)を足す。ID は 8 時間・失効できるのは今と同じ。
- 利点: **ホスト名の使い分け(`127.0.0.1` と `localhost`)の案内が要らなくなる**。責任者が成果物を `127.0.0.1` で開いても、`localhost` で開いても、`dev:ui`(Vite の `localhost:5173`)で開いても、ID は担当に届かない。ADR-0061 の「残ること」の 1 つ目・2 つ目が消える。

### 案 B: IndexedDB の取り出せない鍵で、リクエストごとに署名する(乙。DPoP 的)

- 画面が、WebCrypto で ECDSA P-256 の鍵を `extractable: false` で作り、IndexedDB(オリジンごと)に `CryptoKey` として持つ。合言葉で一度だけ、公開鍵を本体に登録する。
- すべての API 呼び出しに、`Authorization: Kuramoto-Sig <鍵の ID>, <時刻>, <ナンス>, <署名(メソッド+パス+本文のハッシュ+時刻+ナンス)>` を付ける。本体は、登録した公開鍵で検証し、時刻の窓(数十秒)とナンスの重複で、使い回しを断る。
- 利点: 資格情報が**画面の JS からも取り出せない**ので、案 A の弱いところ(XSS・端末のログやディスクから盗まれる)も消える。漏れたリクエストも、窓が過ぎれば使えない。
- 欠点:
  - 案 A の変えるところ(画面のファイルの配り方、画像、ダウンロード)に加えて、署名・検証・ナンスの保持・時計のずれの扱い・本文のハッシュを足す。本体と画面の両方に、試験の要る暗号の部品が増える。
  - 署名の入れ物(ヘッダー)は案 A と同じ `Authorization` なので、**案 A のあとに足せる**(セッション ID を鍵に結びつけるだけ)。最初から作る理由は、今の脅威(担当が Cookie を取る)に対しては無い。
  - WebCrypto は secure context が要る(`http://localhost`・`http://127.0.0.1` は secure context なので動くが、他の PC からの `start:public`(http の LAN アドレス)では動かない)。`start:public` を使い続けるなら、別の道が要る。
  - ブラウザの「サイトデータを消す」で鍵が消える(入り直しになる。案 A も同じ)。

### 案 C: Cookie のまま、ブラウザの機能で届かなくする

- `__Host-` の接頭辞・`Secure`・`SameSite`・CHIPS(Partitioned)は、いずれも**ポートで分けない**。`__Host-` は Path・Domain を縛るだけで、別ポートのサーバーには送られる。
- ポートごとに Cookie を分ける仕組み(origin-bound cookies)は、ブラウザの実験段階で、既定では効かない。当てにできない。

### 案 D: `Origin` / `Sec-Fetch-Site` などのヘッダーで、ブラウザからの要求だけ通す

- 担当は、`Cookie` を貼ってシェルから `curl` するときに、どんなヘッダーでも自分で付けられる。意味が無い。

### 案 E: 前の ADR で見送ったもの(再確認)

- ランダムなホスト名(`k-<乱数>.localhost`): Safari などで名前解決できない。見送りのまま。
- 有効期間をもっと短く: 使い心地が悪い。見送りのまま。

## 推奨

**案 A を実装する。案 B は、案 A のあとに、必要になったら足す(今は足さない)。**

理由:

1. 脅威は「担当のコードが、ブラウザから送られた資格情報を受け取る」こと。案 A はこれを**オリジンの分離**で根本から塞ぎ、責任者の使い方(`127.0.0.1` か `localhost` か)に守りが掛からなくなる。案 B も塞ぐが、この脅威に対しては案 A と差が無い。
2. 案 A の弱点(XSS)は、今の画面に入り口が無く、CSP の保険と、短い期間・失効で抑えられる。案 B の追加の守りは、暗号の部品と `start:public` の制約という大きな費用に見合わない。
3. 案 A の `Authorization` の入れ物は、案 B に伸ばせる。

案 A でも残ること:

- 担当が、責任者のブラウザのプロファイルのディスク(`localStorage` の保存先)を読めれば、ID を取れる。これは、担当のシェルの閉じ込め(ADR-0059 の範囲)の話で、この ADR の範囲外。
- 画面のファイル(JS・CSS)が、合言葉なしで読める(秘密ではない)。
- 本体を再起動すると、セッションは全部切れる(今と同じ)。

## 仮決定(リーダー。責任者の確認待ち)

1. 案 A でよい(案 B は、案 A のあとに、必要になったら足す)。
2. 画面のファイル(`index.html`・JS・CSS・フォント)は、合言葉なしで配ってよい。`/api/` は今までどおり認証する。
3. `start:public`(他の PC から開く)の `http://<LAN のアドレス>` でも、`localStorage` にセッション ID を持ってよい(今の Cookie と同じ程度の露出)。

責任者の回答がこれと違ったら、実装を作り直す。

## 実装に進むときの分け方(責任者が案 A でよいと決めたら)

小さく分ける。

1. 本体: `Authorization: Bearer` でセッション ID を受ける。`POST /api/session`。画面のファイルを認証から外す。Cookie の発行をやめる(古い Cookie を消す応答だけ残す)。`DELETE /api/session` を Authorization の ID で失効する形に。試験(`src/server.test.ts`・`src/sessions.test.ts`)。
2. 画面: `#k=` の取り込み、`api()` の Authorization、`AuthImage`、ダウンロード、401 の案内。CSP。E2E(`e2e/auth.spec.ts`)を `#k=` と `localStorage` に合わせて直す。端末に出す URL・README・ADR-0061 の更新(状態を「置き換えられた」に)。
