# ADR-0015: 企画スタジオの画面デザインの次にインフラの段階を置き、アーキテクトが受け持つ

- 状態: 承認
- 日付: 2026-11-07

## 背景

企画スタジオは 要件 → ユーザーフロー → 画面デザイン → ドメインとデータ の 4 段階で、どこで・どう動かすか(ホスティング・環境・デプロイ・運用・費用)を決める場が無かった。決めないまま実装に入ると、開発が実装しながら決めることになり、後から動かす場所を変えると作り直しが大きく、費用にも実装が終わるまで気づけない。

## 決定

- 企画スタジオに「インフラ」の段階を、画面デザインの次(4 段階目、ドメインとデータの前)に置く。画像のアップロードやオフラインでの保存など、何を用意すべきかは画面まで決まって初めて分かるため。データ設計はインフラで決めたこと(DB の種類など)を前提にする。
  - 当初は要件の直後に置いたが、要件だけでは画面が求めるものが分からず、構成を決めきれないため、同じ日に画面デザインの次へ移した。
- 担当はアーキテクトの広が兼ねる。ドメインとデータの段階と同じく、慎重さを優先する設計の仕事であり、人を増やさない。
- 決めることは 4 つ。順番もこのとおり。
  1. 動かす場所と構成: 既にある環境を使うか、使うサービス、構成要素とつながり(構成図)
  2. 環境とデプロイ: 環境(staging・production など)、CI/CD、マイグレーションの流し方、秘密情報の置き場所
  3. 運用: 監視、ログ、バックアップ、障害時の戻し方
  4. 費用と規模: 見積もりの前提(利用者数・データ量)と月額
- まず登録されたリポジトリ(特にインフラの役割のもの)を読み、既にある環境・IaC・CI を確かめ、使えるものは使う。新しいクラウドの契約やサービスは安易に増やさない([ADR-0009](0009-architect-and-domain-first.md) と同じ考え)。
- 戻せない選択(データの置き場所の国・解約しにくい契約など)と大きな費用がかかる選択は、お任せでも責任者の未決に入れる。
- ほかの段階と同じく、合意する / お任せ / 省く を選べる。
- チームに渡すとき、リポジトリに書けるもの(IaC・設定・ワークフロー)はチケットにする。クラウドの契約やアカウント作成など人が行うことはチケットにせず、責任者に伝える。

## 結果

- インフラは、要件・フロー・画面が求めるものを見てから決められる。
- ドメインとデータの段階は、インフラで決めたこと(DB の種類など)を前提に書ける。
- 既にある環境や予算の制約は、フローや画面を決めた後でしか反映されない。強い制約がある場合は、要件の「やらないこと」や会話で先に伝える。
- 費用の見積もりが実装前に見える。
- 企画の段階が 1 つ増える。省く・お任せで軽くできる。

## 検討した別案

- **要件の直後に置く**(当初の案): 予算や既にある環境の制約をフロー・画面より先に効かせられるが、画面が求めるもの(アップロード・オフラインなど)が分からないまま構成を決めることになる。
- **ドメインとデータの後に置く**: 表やサービスの形が決まってから動かし方を決められるが、DB の種類などインフラの判断がデータ設計に反映されない。
- **ドメインとデータの段階の中の節にする**: 段階は増えないが、インフラだけを省く・お任せにすることができない。
- **インフラ担当を新しく置く**: 方針を別に調整できるが、設計の判断が 2 人に分かれ、人も増える。
