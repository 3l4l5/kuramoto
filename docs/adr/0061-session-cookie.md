# ADR-0061: 画面の Cookie には合言葉そのものを入れず、短期で失効できるセッション ID を入れる

- 状態: 提案
- 日付: 2026-11-14
- チケット: #104(#101 のレビューで見つかった。ADR-0059 の続き)

## 背景

ADR-0059(#101)で、本体の API と画面のすべてに合言葉を掛け、合言葉つきの URL を開くと Cookie `kuramoto_token`(1 年)に**合言葉そのもの**を入れた。
Cookie は**ポートで分けられない**(ホスト名だけで決まる)。責任者のブラウザが、担当が立てた開発サーバー(`http://localhost:5173` など)を開くと、同じホスト名の Cookie がそのサーバー(=担当のコード)に送られる。担当のコードが `Cookie` ヘッダーを作業場所に書き出せば、担当が合言葉を取り、本体の API(`localhost:4300`)でチケットの操作・merge を行える。しかも合言葉は 1 年変わらず、止める手段が合言葉の作り直ししかなかった。

## 決めたこと

**Cookie には、合言葉ではなく、本体だけが検証できるセッション ID を入れる。短期で切れ、失効できる。成果物は別のホスト名で開くよう案内する。**

1. **セッション ID(Cookie `kuramoto_session`)**(`src/sessions.ts`)
   - 合言葉つきの URL(`/?token=…`)を開くと、本体が 32 バイトの乱数のセッション ID を新しく作り、Cookie(HttpOnly・SameSite=Strict・Path=/・**8 時間**)に入れて、合言葉を外した URL へ送り直す。開くたびに別の ID になる。
   - 本体は ID の SHA-256 だけをメモリに持つ(期限つき)。期限が来たもの・失効させたものは通さない。メモリなので、**本体を再起動すると全部失効する**(責任者は端末に出る URL を開き直す)。
   - 合言葉(`~/.kuramoto/access-token`)は Cookie にもどこにも出ない。Cookie が担当のサーバーに届いても、担当が得るのは、8 時間で切れ、失効できる ID だけ。合言葉は漏れず、ID が止まれば、また担当は本体に入れなくなる。
   - `Authorization: Bearer` は合言葉だけを受ける(セッション ID を Bearer に入れても通らない)。責任者のスクリプト用。
2. **失効**(合言葉は作り直さなくてよい)
   - `DELETE /api/session`: このブラウザのセッションを失効させ、Cookie を消す。
   - `POST /api/session/revoke-all`: すべてのセッションを失効させる(漏れた疑いがあるとき)。止めた数を返す。
   - どちらも、通常どおり認証(セッションか合言葉)と `x-kuramoto: 1` ヘッダーが要る。本体の再起動でも全部切れる。合言葉まで変えたいときは `~/.kuramoto/access-token` を消して再起動する。
3. **前の版の Cookie は通さない**: 前の版が入れた `kuramoto_token`(合言葉そのもの。すでに担当のサーバーに届いた可能性がある)は、もう通らない。見つけたら 401 や送り直しの応答で `Max-Age=0` を返して、ブラウザから消させる。**前の版を動かしたことがあれば、合言葉は漏れた前提で、`~/.kuramoto/access-token` を消して再起動し、作り直す。**
4. **成果物は、本体と別のホスト名で開く**: 端末に出す URL を `http://127.0.0.1:<port>/?token=…` にし、担当が動かした成果物は `localhost` で開くよう端末・README で案内する。Cookie はホスト名ごとなので、`127.0.0.1` の Cookie は `localhost:<任意のポート>` のサーバーには送られない。(担当の成果物の案内先は Kuramoto の画面が出すものではない。担当が `127.0.0.1:…` を案内したり、責任者が成果物を `127.0.0.1` で開いたりすると、この守りは効かず、①の「短期・失効」だけで守ることになる。)
5. 壊れた `%` を含む Cookie で `decodeURIComponent` が落ちないようにした(`parseCookies`)。

## 選ばなかったこと

- **案内だけ(別プロファイルで開く・別ホスト名で開く)**: 守れるかが責任者の注意に掛かり、漏れたときに止める手段も無い。④だけでは、担当が `127.0.0.1` に誘導する(開発サーバーを `127.0.0.1` で案内する・`localhost` のページから `127.0.0.1` へ飛ばす)と破れる(SameSite=Strict でも、飛んだ先のページからの同じサイト内の取得には Cookie が付く)。①②で、破られても被害を小さく・止められるようにしたうえで、④を足す。
- **セッション ID だけ(案内なし)**: 漏れた ID は、期限が切れるか失効させるまで、担当が使える(Cookie の送り先はブラウザが決めるので、サーバー側では「ブラウザから来た」と「担当が貼り直した」を見分けられない)。8 時間は、守りとしては緩い。④の案内を足して、そもそも届かない道を作る。
- **Cookie をやめて、ページの JS が保持する資格情報(`localStorage`・`Authorization` ヘッダー)にする**: Web Storage は**オリジン(ポートまで含む)ごと**に分かれるので、担当の別ポートのサーバーには届かない。根本の解決だが、HTML・画像・ダウンロードなどヘッダーを付けられない読み込みの作り直し(HTML 自体を合言葉なしで配る)が要り、XSS で盗まれる(HttpOnly を失う)。大きな変更なので別のチケットで検討する。
- **有効期間をもっと短く(15 分など)・使うたびに延ばす**: 責任者が頻繁に URL を開き直すことになり使い心地が悪い。延ばす方式は、担当が貼り直して使い続けても切れない。8 時間の固定にした(1 日の作業の長さ)。
- **ランダムなホスト名(`k-<乱数>.localhost`)で配る**: 担当が誘導先を推測できず、Cookie が漏れない強い案だが、`*.localhost` を名前解決できないブラウザ・環境がある(Safari など)。Vite の開発サーバー(`dev:ui`)・E2E・README の案内も変わる。見送り。
- **ブラウザごとに鍵を持たせて署名する(DPoP 的な方式)**: IndexedDB の鍵(オリジンごと・取り出せない)で、すべてのリクエストに署名させる。担当のサーバーは Cookie を取れても署名できない。根本の解決の候補だが、すべての読み込みの作り直しになる。別のチケットで検討する。

## 残ること

- 担当が成果物を `127.0.0.1` で案内する・責任者が `127.0.0.1` で開く・担当が `localhost` から `127.0.0.1` へ飛ばす、のいずれかがあると、8 時間のあいだはセッション ID が担当に渡りうる。被害は、その ID の期限(8 時間)か失効(`revoke-all`・再起動)まで。
- `dev:ui`(Vite、`localhost:5173`)で画面を作るときは、本体の URL も `localhost` で開き直す必要があり、その間は④の守りが効かない(README に書いた)。Kuramoto 自身を作る人の使い方で、担当の成果物とは別。
- セッションはメモリなので、本体を再起動すると責任者も入り直す。長く使いたい要望が出たら、ID のハッシュをファイルに持つ。
- 画面の「ログアウト」「すべてのセッションを失効」のボタンは、本部の下の「アクセスの管理」に付けた(#105)。API を呼ぶのは `ui/src/session.ts` だけ。成功すると画面の上に「ログアウトしました」の案内を出し、合言葉つきの URL を開き直す(読み込み直す)まで出し続ける。「すべて失効」は、このブラウザも入れなくなるので、確認の面を挟む。
- 上の「選ばなかったこと」の 2 つ(JS が持つ資格情報・鍵の署名)は、Cookie が担当に届くこと自体を無くす。ADR-0062(#106)で検討した(推奨は localStorage + Authorization。実装は責任者の確認のあと)。
