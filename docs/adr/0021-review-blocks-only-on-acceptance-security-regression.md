# ADR-0021: レビューで止めてよいのは、受け入れ条件・セキュリティ・この差分の不具合だけにする

- 状態: 提案
- 日付: 2026-11-09

## 背景

チケット #10(一覧の外枠)は、レビュー・セキュリティ・QA の往復が 7 回まで続いた。必須の指摘は 2 往復目までに直っていたが、次のことで終わらなかった。

- セキュリティの担当が「ベースのブランチが進んで、この PR が merge できなくなった」を 4 往復続けて差し戻し直した。merge できるかは Kuramoto が merge 待ちで確かめる仕事で、レビューで止める必要が無い。
- ゴミ箱の画面・自動保存の競合・数千件での性能など、後のチケットで扱うことを指摘していた。
- レビュー担当には「不具合と保守を難しくする点を指摘する」とだけ伝えていて、受け入れ条件を判断の基準にしていなかった。重さの線引きが担当ごとにばらついた。
- サンドボックスのせいで QA がテストもブラウザも動かせず、コードを読んだだけの指摘が増えた([ADR-0020](0020-confine-agents-to-worktree.md) で直した)。

## 決定

- 確認の担当(レビュー・セキュリティ・QA)に、チケットの受け入れ条件と、ひも付く要件(R1 など)の受け入れ条件を、判断の基準としてはっきり渡す。
- 必須(PR を止める指摘)にしてよいのは次の 3 つだけ。指摘に根拠(`basis`)を付けさせ、根拠の無い必須の指摘は道具が受け付けない。
  - `acceptance`: 受け入れ条件を満たしていない
  - `security`: セキュリティの問題
  - `regression`: この差分で入った不具合
- それ以外は提案(PR を止めない)にする。
- チケットの範囲外のことは、指摘にせず「別チケットの候補」(`followups`)として出させる。Kuramoto がチケットにし、リーダーが交通整理で順番と担当を決める。同じタイトルのチケットは重ねて作らない。
- ベースのブランチとの衝突・merge できるかどうかはレビューで見ない。
- 確かめる道具が動かないことを理由に差し戻さない。確かめられた範囲で判断し、動かせなかったことは提案として書く。
- 再レビューで、前回の指摘が上の 3 つに当たらないもの・範囲外のものなら、reopen せず accept する。

## 結果

- 往復は、受け入れ条件・セキュリティ・不具合が直るまでに限られる。好みや範囲外の話で止まらない。
- 範囲外の指摘は捨てられず、別チケットとして後に回る。チケットは増えるが、リーダーが交通整理で並べる。
- 指摘の重さを決めるのは担当だが、根拠を付けさせるので、ばらつきが減る。

## 検討した別案

- **往復の上限を下げる**: 早く責任者に上がるだけで、往復の原因(範囲外の指摘・レビューの仕事でないこと)は残る。
- **レビューの厳しさ(strictness)を「重要」にする**: 指摘が減るが、受け入れ条件を基準にすることにはならない。範囲外の指摘を拾い直す仕組みも無い。
